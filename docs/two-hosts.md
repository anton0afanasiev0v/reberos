# Два физических хоста: развёртывание через канал 2 МБ/с

Лаборатория изначально рассчитана на один хост: оба «узла» — это два
compose-проекта в общем docker-мосте `kerberos` (172.30.11.0/24).
Если Узел А и Узел Б — **разные машины**, мост не работает (bridge живёт
в пределах одного демона), и весь трафик между узлами идёт через
внешний канал.

Этот документ — схема развёртывания на двух хостах с упором на
**минимизацию объёма передачи**: канал 2 МБ/с — это ~16 Мбит/с, и
450 МБ образов едут по нему 3,7 минуты, а каждый лишний повторный
`docker build` на втором узле — это ещё несколько сотен мегабайт.

---

## 1. Что реально пересекает канал

| Поток | Объём | Комментарий |
|---|---|---|
| Kerberos (AS-REQ, TGT, GSSAPI), OIDC-токены | **1–5 КБ** на операцию | ограничение 2 МБ/с на это не влияет: вся проверка лаборатории — меньше мегабайта |
| Базовые образы + apt-слои на Узел Б | **~450 МБ** (один раз) | главный поток; Keycloak — 253 МБ из них |
| Репозиторий (git clone с GitHub) | **0,5 МБ** | после удаления из истории бинарника `.vscode/browse.vc.db` |
| Рабочее дерево при rsync | **1,3 МБ** | `.vscode/browse.vc.db` (1,3 ГБ) исключается из переноса |
| Повторный деплой | **≈ 0** | rsync пропускает неизменившиеся файлы бандла |

Вывод: 2 МБ/с ограничивает не работу лаборатории, а **развёртывание**.
Поэтому весь план — собрать образы один раз и перенести их, а не
каждому узлу качать своё.

---

## 2. Схема сети: `network_mode: host`

Между хостами — L3 (интерфейс + статические маршруты), общего L2-сегмента
нет, поэтому `macvlan`/общий мост неприменимы. Варианты:

### Вариант А (рекомендуемый): host-network

Контейнеры узла работают в сетевом пространстве самого хоста
(`network_mode: host`), а имена лабораторных сервисов резолвятся через
`/etc/hosts` хоста.

```
┌──────────── Узел А (хост A) ────────────┐        ┌──── Узел Б (хост B) ────┐
│ kdc-a1  kdc-a2  ldap-a  web-a            │  канал │ kdc-b3  kdc-b4  ldap-b   │
│ keycloak-a  portal-a   → порты хоста:     │ 2 МБ/с │ keycloak-b  portal-b     │
│   88, 389, 80, 8000, 8080                │◄──────►│   88, 389, 80, 8000,    │
│ /etc/hosts:                              │        │   8080                  │
│   web-a.lab.test → 127.0.1.1             │        │ /etc/hosts:             │
│   web-b.lab.test → IP хоста B            │        │   web-b.lab.test → 127.0.0.1│
└──────────────────────────────────────────┘        │   web-a.lab.test → IP A  │
                                                       └────────────────────────┘
```

Плюсы: ноль настройки маршрутизации/NAT/iptables; имена в `/etc/hosts`
одни и те же для всех; Kerberos/SPNEGO работают без правок, потому что
билет всегда выдаётся на имя (`HTTP/web-a.lab.test`), а не на IP.
Docker копирует `/etc/hosts` хоста внутрь контейнеров при host-network —
отдельные `extra_hosts` не нужны.

Минусы: `hostname:` у контейнеров игнорируется (не критично: все имена
из `krb5.conf` — доменные), порты 88/389/80/8000/8080/9000 занимаются
на хосте, админка Keycloak открывается на `http://<хост>:8080/auth`.

### Вариант Б: мосты + маршрутизация

Узел А: мост `172.30.11.0/24`, Узел Б: свой мост `172.30.12.0/24`,
между ними `ip_forward` + MASQUERADE + статический маршрут, а `/etc/hosts`
указывает на IP контейнеров. Сохраняет IP-адреса из README, но требует
правок ядра и правил firewall на обоих хостах, плюс отдельный env для
каждого узла (разные подсети). Трафик по каналу — тот же (килобайты).

## 3. Подготовка хоста

На **обоих** хостах:

```bash
# docker + утилиты переноса
sudo apt-get install -y docker.io docker-compose-v2 rsync zstd

# имена лабораторных сервисов
# Узел А:
./scripts/install-hosts.sh a <IP-хоста-Б>      | sudo tee -a /etc/hosts
# Узел Б:
./scripts/install-hosts.sh b <IP-хоста-А>      | sudo tee -a /etc/hosts
# ПК оператора (браузер, kinit):
./scripts/install-hosts.sh client <IP-A> <IP-B> | sudo tee -a /etc/hosts
```

Проверить, что имена видны и порты отвечают:

```bash
getent hosts web-a.lab.test web-b.lab.test
```

Свободные порты на хосте: **88/tcp+udp, 389, 80, 8000, 8080, 9000**.
Если что-то из этого занято — выносите соответствующий сервис на другой
порт в `compose-node-*.host.yml` (и правьте `WEB_x_PORT` в `deploy/env-*.env`).

## 4. Развёртывание

### Шаг 1. Узел А: собрать образы (один раз)

```bash
./scripts/build-images.sh
```

Собираются 6 образов с общими тегами `lab/kdc:1`, `lab/ldap:1`,
`lab/apache:1`, `lab/keycloak:1`, `lab/portal:1`, `lab/client:1`
(а не по образу на каждый сервис — KDC узла А и KDC узла Б это один и
тот же Dockerfile).

### Шаг 2. Перенести образы на Узел Б

Основной режим — бандл: `docker save` → `zstd` → `rsync` → `docker load`.

```bash
./scripts/sync-node-b.sh --peer user@<IP-хоста-Б>
```

Скрипт сам соберёт бандл, покажет объём и время, перенесёт только
изменившиеся файлы и загрузит образы на Узле Б. На Узле Б нужны
`docker`, `zstd`, `rsync` и ssh-доступ по ключу.

Альтернативы:

```bash
# У Узла Б есть интернет — образы он тянет сам, по каналу А↔Б идёт
# только репозиторий (~1 МБ):
./scripts/sync-node-b.sh --peer user@<IP-хоста-Б> --mode build

# Локальный registry на Узле А (docker pull вместо файлов):
docker compose --env-file .env --env-file deploy/env-a.env \
    -f compose-node-a.yml -f compose-node-a.host.yml --profile registry up -d registry
./scripts/sync-node-b.sh --peer user@<IP-хоста-Б> --mode registry --registry <IP-хоста-А>:5000
# на Узле Б: /etc/docker/daemon.json -> {"insecure-registries": ["<IP-A>:5000"]}
```

### Шаг 3. Поднять узлы

Узел А:

```bash
docker compose --env-file .env --env-file deploy/env-a.env \
    -f compose-node-a.yml -f compose-node-a.host.yml up -d
```

Узел Б:

```bash
docker compose --env-file .env --env-file deploy/env-b.env \
    -f compose-node-b.yml -f compose-node-b.host.yml up -d
```

Клиент (на хосте оператора или на Узле А):

```bash
docker compose --env-file .env --env-file deploy/env-a.env \
    -f compose-client.yml -f compose-client.host.yml up -d
```

## 5. Проверка

```bash
./scripts/verify-remote.sh
```

Скрипт поднимает Узел А и клиента локально, Узел Б **не трогает** (он
уже поднят на соседней машине), проверяет доступность его сервисов по
сети (`kdc-b3:88`, `ldap-b:389`, `web-b:80`, `keycloak-b:8080`,
`portal-b:8000`) и прогоняет все 28 проверок лаборатории, включая
негативные межузловые тесты (билет ORG1 не должен открывать `ldap-b`/`web-b`).

Ожидаемый объём трафика по каналу за прогон: **< 1 МБ**.

## 6. Откат в демо-режим

Демо-режим (один хост, общий мост) не затронут — он использует базовые
compose-файлы без override'ов:

```bash
./scripts/reset.sh
./scripts/verify.sh
```

## 7. Подводные камни

- **Имена, а не IP.** SPNEGO выдаёт билет на имя из URL: если вместо
  `web-b.lab.test` подставить IP, SPNEGO не сработает. Отсюда
  `/etc/hosts` на всех машинах, включая ПК оператора.
- **Админка Keycloak** в host-network доступна на `http://<хост>:8080/auth`
  (в демо-режиме это `127.0.0.1:8091`/`8092`). Слушает все интерфейсы —
  при необходимости закройте порт firewall'ом.
- **`docker compose up --build` на Узле Б** заново скачает базовые образы
  и apt-пакеты (~450 МБ). Не делайте этого: на Узле Б образы уже
  загружены, поэтому `--build` не нужен.
- **Тома `keytabs-*`** живут на своём узле; общие keytabs между узлами
  не нужны (у каждого узла свои KDC).
- **`monitoring/`** в репозитории — конфигурация старой однопакетной
  схемы (имена `kdc.lab.test`, подсеть 172.30.10.0/24) и в compose не
  подключена. К двум хостам не относится.
